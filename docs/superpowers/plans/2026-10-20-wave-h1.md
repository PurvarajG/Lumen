# Wave H1: Outputs menu that works, and a calmer, less boxy console (2026-10-20)

Plan for **gpt-6.1-sol (high) as orchestrator only**. Sol does not write Rust. It hands each phase to a small **gpt-6-luna** worker, reviews the diff, runs the final checks and commits. Written by Claude Opus. `development` is at `3050514` (rc.6).

## Rules for the orchestrator (read first)

- **Saving credits is a hard requirement.**
  - Sol reads this file, worker reports and `git diff`s. Sol never opens `app.rs` (2,630 lines) or other large files whole. Use `rg -n` and `sed -n a,bp` on the lines a diff touches.
  - Each phase below is a self-contained brief. To start a worker, pass it **this file's path and the phase heading**, e.g. "Execute section H1.1 of docs/superpowers/plans/2026-10-20-wave-h1.md". Do not rewrite or summarise the section.
  - Workers: `gpt-6-luna`, medium reasoning. If a worker fails its acceptance twice, first rewrite the failing step more narrowly. Only if it fails a third time, rerun that phase with `gpt-6.1-sol` as the worker (per AGENTS.md).
  - Workers write a report of 15 lines or fewer to `.local/logs/h1-<phase>.md`: files changed, commands run with pass/fail, anything they did differently and why. Sol reads only this report and the diff.
- Launch workers with `.local/run-worker.sh codex h1-<phase> gpt-6-luna docs/superpowers/plans/2026-10-20-wave-h1.md`, after `git worktree add .local/wt/h1-<phase> -b wave/h1-<phase> development`. The Codex sandbox cannot write `.git`, so Sol commits each worker's changes on its branch, then merges into `development`.
- **One shared build dir:** set `CARGO_TARGET_DIR=$PWD/.local/targets/h1` for every worker by editing the export line in `run-worker.sh` for this wave (restore it afterwards). Dependencies compile once, and cargo's lock runs parallel builds one at a time. This laptop has about 20 GB free disk and 24 GB RAM. Delete `.local/targets/h1` and the worktrees after the wave.
- Order: **H1.0 → H1.1 → H1.2 → (H1.3a, H1.3b, H1.3c at the same time) → H1.4.** H1.1 and H1.3a both edit `app.rs`, and H1.2 sets the tokens H1.3 uses, so those steps run one after another. The three H1.3 workers own separate files.
- Workers check only what they changed: `cargo check -p lumen-app`, `cargo clippy -p lumen-app --all-targets -- -D warnings`, `cargo test -p lumen-app`. The full workspace checks run once, in H1.4.
- Every worker reads and follows `~/.claude/skills/ponytail/SKILL.md`. UI workers (H1.2, H1.3x) also read `~/.claude/skills/taste-skill/SKILL.md` and `~/.claude/skills/impeccable/SKILL.md`, adapted to egui, and follow `DESIGN.md`. **DESIGN.md wins over the skills** where they disagree. The taste skill is written for landing pages, so its hero, bento, GSAP, image, dark/light dual-mode and marketing-copy rules do not apply here.
- No new dependencies. No changes to layout structure, pane names, menu labels or keyboard shortcuts (operators rely on muscle memory). Do not push.
- If a step does not fit the code a worker finds, the worker stops that step, says why in its report, and does the closest correct thing. Workers never work around a problem silently.

## H1.2 One shape, fewer outlines, space between panes (tokens only)

Files you own: `crates/lumen-app/src/style.rs`, `crates/lumen-app/src/dock.rs` (`dock_style` only). Do not edit call sites.

1. **Radius lock** (record it in a comment above `install`): controls 6, surfaces 8 (menus, popups, panes, tiles, drop zone), windows and modals 8, status pills fully rounded. Add `pub const RADIUS: u8 = 6;` and `pub const RADIUS_SURFACE: u8 = 8;`. In `install`, set `corner_radius = RADIUS` on all five `v.widgets.*` states, and set `v.menu_corner_radius` and `v.window_corner_radius` to `RADIUS_SURFACE`. `primary()` uses `RADIUS`.
2. **Buttons without outlines, form controls keep theirs.** egui uses the same `widgets.inactive.bg_stroke` for buttons, checkboxes, radios and text fields (`checkbox.rs:110`, `radio_button.rs:88`, `text_edit/builder.rs:451`). Removing it globally would make checkboxes and fields hard to see. That breaks DESIGN.md's contrast rule, so keep the global stroke. Instead, add one function:
   ```rust
   /// Ghost buttons: no fill or outline until hovered. For rows of secondary actions only.
   pub fn ghost(ui: &mut egui::Ui) { let w = &mut ui.visuals_mut().widgets; w.inactive.weak_bg_fill = Color32::TRANSPARENT; w.inactive.bg_stroke = Stroke::NONE; }
   ```
   H1.3 calls it at the start of a `ui.horizontal` scope. Also set `v.widgets.hovered.bg_stroke = Stroke::NONE`, because the hover fill change is enough feedback and the stroke adds a box on hover.
3. **Space instead of lines between panes** (`dock_style`): `separator.width = GAP` (8), `color_idle = CANVAS`, `color_hovered = LINE`, `color_dragged = SAFFRON`; `tab_bar.hline_color = Color32::TRANSPARENT`; `tab.tab_body.bg_fill = PANEL`; give `tab_bar.corner_radius` rounded top corners and `tab.tab_body.corner_radius` rounded bottom corners, both `RADIUS_SURFACE`; dock tab `corner_radius` = `RADIUS`; `dock_area_padding = Some(Margin::same(GAP as i8))`. The `CentralPanel` that hosts the dock must fill `CANVAS` so the gaps show the window ground. Find it with `rg -n "DockArea" crates/lumen-app/src` and report the line. If it lives in `app.rs`, change only its `.frame(...)`, and say so in the report.
4. Read the field names in `~/.cargo/registry/src/*/egui_dock-0.18.0/src/style.rs` before writing. If a field does not exist under that name, use the nearest equivalent and say so in the report.

Acceptance: check/clippy/test pass. Native capture of Present at 1500 pt (`.local/qa/h1/h1.2/`): panes read as rounded `PANEL` surfaces on a darker ground with an 8 pt gap; dragging a separator still resizes and turns saffron; dropping a tab still shows the saffron drop areas; checkboxes and text fields are still clearly outlined.

## Out of scope (pushed back, ponytail ultra)

- **Merging the two header rows into one, or moving Shortcuts/Reset layout into a menu.** That changes where operators look for things. Ask the user first.
- **New UI animation** (tweened hover colours, sliding panels, popup springs). DESIGN.md caps motion at 2 for a live console. egui does not tween widget colours, and a custom tween layer is real code for a small gain.
- **A light theme.** The taste skill asks for dual themes on consumer pages. This is a dim-room operator console, and DESIGN.md is dark-only on purpose.
- **Removing em dashes across the app.** Only the display label (H1.1) changes, because it is in code this wave touches. A full copy pass is its own small task.
- **Headless egui click tests for the Outputs menu.** `egui_kittest` is not a dependency, and hand-made pointer-event tests would break easily. The native click test in H1.1 covers it.
