## What was found (evidence)

| # | Observation | Phase |
|---|---|---|
| 1 | **Two identical monitors are told apart only by macOS's "(1)"/"(2)" name suffix.** `DisplayKey` is `{name, width, height}` (`displays.rs:12`) and `match_display` matches on those (`displays.rs:42`). macOS hands out the suffix by enumeration order, so after a reboot or cable swap "(1)" can be the other physical monitor and the audience opens on the stage screen. | H2.1 |
| 2 | **Display sizes are in points, not pixels.** `enumerate` uses `CGDisplayPixelsWide/High` (`displays.rs:274`), which give 1920 × 1080 for these 4K panels. The Outputs menu therefore says "1920 × 1080", and `media::video_output_size` (`media.rs:49`) falls back to that size, so a video started before the audience window opens decodes at 1080p (known G3.1 gap). | H2.2 |
| 3 | **Transition stutter, cause 1 (fixed, uncommitted).** During a fade the console repainted every vsync at 120 Hz while the audience also animated; both windows paint on one thread, so audience frames landed unevenly. Video already throttled the console to 16 ms; transitions now do the same (`app.rs` near `// Transitions and video repaint every frame`). Plain fades also now use the same eased curve as caption fades (`render.rs`, `Transition::Fade` arm). **Not yet measured on hardware.** | H2.0, H2.3 |
| 4 | **Transition clock starts before the first frame.** `OutputTransition.started = Instant::now()` is set when the cue fires (`app.rs:2178`, `app.rs:2250`). If that frame is slow (new texture upload, text layout), the first visible frame is already 30-60 % through the fade, which reads as a jump. | H2.3 |
| 5 | **Text that stays the same dims mid-fade.** When only captions change over a shared background, old and new text are both painted at `(1-t)` and `t` (`render.rs` `paint_transition_layers`, shared-background branch). Where a line is identical on both slides (lyrics, repeated headers), it drops to about 75 % brightness at the midpoint and comes back: a visible flicker. | H2.3 |
| 6 | **Push text wobbles.** epaint rounds text to whole pixels (`TessellationOptions::round_text_to_pixels`, default true, `epaint-0.33.3/src/tessellator.rs:685`) while backgrounds move by fractions of a pixel, so during a Push the text shifts by up to 1 px against its background. | H2.3 |
| 7 | **"Play in PowerPoint" hands the audience screen to PowerPoint.** `deck.rs:37` runs `activate` and a presenter-type slideshow, and Lumen's audience window has to get out of the way. The user finds this switch fragile and wants animated PowerPoint decks to play inside Lumen. macOS has no way to embed another app's slideshow, and reimplementing PowerPoint animations is out of scope. Candidate: PowerPoint plays in a *window* that Lumen captures with ScreenCaptureKit and paints as a media layer, while Next/Previous keep using the existing AppleScript. | H2.4, H2.5 |

Existing tools to reuse: `.local/qa/g1/cadence-lossless.sh` (lossless avfoundation capture of one display, prints how many refreshes each picture stayed up), the HTTP control API (`lumen-control`, `POST` commands such as `Next`, default `127.0.0.1:47800`, token in Settings; enable it in the test data dir's settings), `--project <file>`, `--smoke-test`, `LUMEN_DATA_DIR` for a throwaway settings folder, and `.local/qa/lumen test deck.ppt`.

Follow the raw-FFI style already in `displays.rs`; no new crate.
2. `DisplayKey` equality is used for matching and for `needs_replace`. Do **not** let a missing uuid in an old saved key break the exact match: write the match order explicitly in `match_display`:

   2. same name and resolution;
   3. same name;
   4. the only non-primary display.
   Implement equality for step 2 on name+width+height, not derived `==` on the whole struct, or change `DisplayInfo`/`needs_replace` comparisons accordingly. Keep the existing doc comment's shortcut note accurate.
3. When a saved key matches by step 2-4 and the matched display has a uuid, write the upgraded key back to settings once (so old settings migrate), and persist.
4. Tests in the existing `displays.rs` test module: two displays with the same name and size but different uuids, saved uuid picks the right one even when their order is swapped; old saved key without uuid still matches by name; uuid that no longer exists falls through to name, then sole non-primary.

## H2.3 Smooth transitions

Files: `crates/lumen-app/src/render.rs`, `crates/lumen-app/src/app.rs` (transition creation and the audience viewport closure only).

Do these in order, re-measuring with the H2.0 method after each. Stop adding fixes once the acceptance below holds; note any fix you skipped and why.

1. **Start the clock on the first audience frame.** Make `OutputTransition.started` an `Option<Instant>` (None until painted). The audience viewport clones state from a shared mutex each frame, so set `started` there when it is None and write it back to the shared state (the same lock it already takes). The console preview uses that same start if set, else `Instant::now()` for its own paint. `progress()` returns 0.0 while unstarted. Update the existing transition tests (`waiting_transition_holds_the_previous_scene_even_for_cut`, `zero_duration_finishes_instantly_and_progress_is_clamped`) and add one: an unstarted transition has progress 0 and is active.
2. **Identical text does not dip.** In the shared-background branch of `paint_transition_layers`, a text object present on both slides with the same content, frame and style is painted once at full opacity; only the objects that differ crossfade. Reuse the slide object types' existing equality if they derive `PartialEq`; otherwise compare the fields that affect painting. Add a render test in the style of `caption_transitions_paint_shared_video_once_at_full_opacity` that counts shapes or checks opacity for an unchanged object at t = 0.5.
3. **Push text moves smoothly.** While a Push transition is active, set `ctx.tessellation_options_mut(|o| o.round_text_to_pixels = false)` in the audience viewport and restore `true` when it ends (sharp static text matters more than motion the rest of the time). Do the same for the console's live preview only if it is visibly worse there.
4. **Acceptance (recorded in `.local/qa/h2/after.txt` and STATUS):** on LG (1) at 60 Hz with the console on the 120 Hz built-in and the stage open on LG (2), during each 400 ms fade at least 95 % of pictures stay up exactly 1 refresh and none stays up 3 or more. Ask the user to watch one run of the fades show and confirm it looks smooth; write their answer in STATUS verbatim.

## H2.5 PowerPoint inside Lumen (only if H2.4 says go)
