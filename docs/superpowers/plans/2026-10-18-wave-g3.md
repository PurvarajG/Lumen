## G3.1 Full-resolution output (P0, user request: "don't down-res")

Goal: what reaches the audience display is never scaled below that display's own pixel size, up to 3840×2160.

Files: `crates/lumen-app/src/media.rs`, `crates/lumen-app/src/app.rs` (`Published`, audience closure, `paint_live`), `crates/lumen-app/src/render.rs` (`SlideObject::Image` painting), `crates/lumen-app/src/thumbnails.rs` only if you reuse its workers.

1. **Video size follows the output.** Replace the hard-coded 1920×1080 in `MediaState::load_video` with the audience output's physical pixel size: the audience window's inner rect × its `pixels_per_point`, published from the audience closure (it already publishes into `Published`). Before the audience has ever opened, use the largest connected display's pixel size. Cap at 3840×2160. `fit_size` already never upscales, so a 1080p clip stays 1080p. If the output size changes while a video plays, do not reopen the player; the next load uses the new size.
2. **Measure the cost before keeping it.** Make a 4K30 test clip (`ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=30 -t 20 -pix_fmt yuv420p .local/qa/g1/clip4k.mp4`). Play it on the L27q (2560×1440, so it decodes at 2560×1440) with the audience open and record CPU (Lumen + ffmpeg) and `cadence-lossless.sh` numbers next to the 1080p clip. Then fake a 3840×2160 output size (temporary env var or a debug override you delete afterwards) to measure 4K decode on this Mac. If the reader cannot keep 30 fps at 4K, or CPU goes above about 60% of one core, check whether `player.rs` already passes `-hwaccel videotoolbox`; add it if not (it is an ffmpeg flag, not a dependency). If 4K still cannot keep up, cap at 2560×1440 and write the measured numbers and the cap into STATUS. Do not ship a cap you have not measured.
3. **Overlay images at full size.** Object images (logos, overlay props, any `SlideObject::Image`) on the audience, stage and LIVE monitor use a full-resolution texture: decode with the same `image::ImageReader` + limits code as `media.rs:85` (move it into one function both call; keep its 64 MiB and 8192 px limits), on a worker thread, cached by path in a small map next to the existing image texture. Paint the full texture when it is ready, the thumbnail until then. The Cues grid and running-order thumbnails keep the small tier. Evict entries whose path is no longer referenced by the project or the live output.
4. Tests: a unit test that the video size picks the output size, falls back to the largest display, and caps at 3840×2160. Keep `fit_size`'s existing tests.
5. Verify natively: a 300×300 PNG logo and a 1920×1080 PNG overlay prop on the L27q, captured before and after (window capture of the audience). Report the sharpness numbers the way G2.2 did (variance of the Laplacian via `magick`) and the CPU numbers from step 2.

## G3.2 Displays that survive LED processors and cable drops (P0)

Goal: once the operator picks the LED/projector output, the audience goes back to it by itself after a resolution change or a cable drop, and never silently sits on the laptop.

Files: `crates/lumen-app/src/displays.rs`, `crates/lumen-app/src/app.rs` (display scan near line 1035, `show_outputs` placement around `audience_placed` / `stage_placed`).

1. **Matching:** `match_display` tries, in order: same name and resolution; same name (any resolution); if the saved display was not the primary and exactly one non-primary display is connected, that one. Otherwise `None` as today. Keep the doc comment honest about the new rule. Update `saved_display_requires_name_and_resolution_match` and add tests for each step.
2. **Return after a drop:** when the matched display changes (it disappears, then reappears, or a new match is found), re-place the open audience/stage window on it and restore fullscreen, using the same windowed-then-fullscreen sequence as `1d9d9ff`. Read the current placement code before changing it; the fix should be a reset of `audience_placed` / `stage_placed` when the matched display's identity or origin changes, not new placement code. Put the "has the target moved" decision in a small pure function with a test.
3. While the saved display is missing, keep the existing status text and also show it in the Outputs section in the warning colour, so the operator sees it without reading the status bar.
4. Verify natively what you can: change which display is saved, and simulate a disappearing display by a debug override of `enumerate_displays` (deleted afterwards). **Ask the user** in your final report to do two physical checks you cannot do: unplug and replug the L27q while the audience is fullscreen, and set the L27q to 60 Hz once and run `cadence-lossless.sh` with the 30 fps clip. Write those as "Not verified by hand" until they are done.
5. STATUS tip for the operator (no code): set the LED processor to take a 16:9 input at its native input resolution (1920×1080 or 3840×2160) at 60 Hz (50 Hz for 25 fps content), full-range RGB.

## G3.3 Shows that move between Macs (P0, user request)

Goal: a show saved on one Mac opens on another with every photo, video, sound and deck, and old shows are easy to reopen and reuse. Save stays atomic, and so does recovery autosave.

Files: `crates/lumen-core/src/storage.rs` (+ its tests), `crates/lumen-core/src/model.rs` only if a helper to visit all paths belongs there, `crates/lumen-app/src/app.rs` (File menu, `save`, `poll_files`), `crates/lumen-app/src/file.rs`, `crates/lumen-app/src/settings.rs`, `crates/lumen-app/src/main.rs`.

1. **One path visitor.** Add `Project::paths_mut(&mut self) -> impl Iterator<Item = &mut PathBuf>` (or a `for_each_path_mut` closure if the borrow checker fights an iterator) covering all 7 places in evidence row 7, including empty `Document.source`. Every later step uses it, so a future path field has one place to be added. Test: a project with one of each yields 7 paths.
2. **Relative paths on save, absolute in memory.** `save_project` writes a clone in which every path inside the show file's folder is stored relative to it (`strip_prefix` of the canonical folder). `load_project` resolves relative paths against the show file's folder. Paths outside the folder stay absolute. In memory, paths are always absolute, so render, media and thumbnails are unchanged. Tests: round trip inside and outside the folder; a show folder moved to a new location still resolves; an old show with absolute paths loads unchanged.
3. **File → "Save with media…"** (shortcut: none). Pick a folder name with the save dialog; write `<Name>/<Name>.lumen.json` and copy every referenced file that exists into `<Name>/Media/` (one copy per source path; on a file-name clash add ` 2`, ` 3`, …). Deck PDFs from the `decks/` cache are copied like any other file. Then save with relative paths (step 2). Run the copying on the file worker thread with progress in the status bar, the same way Add files reports progress. A missing source is skipped and listed in the result ("3 files were missing and were not copied: …"). After a successful save the app's current path is the new show file. Never overwrite an existing folder: if it exists, say so and stop.
4. **Missing media on open.** After a project opens, count paths that do not exist (on a worker; the check touches the disk). If any are missing, show a banner like the recovery banner: "12 media files are missing — Locate folder…". "Locate folder…" picks a folder and relinks each missing path to a file with the same file name found under it (depth ≤ 4, first match by name, files only). The relink is one undo step and marks the show dirty. Show how many were found and how many are still missing.
5. **Reopen and reuse.** `Settings.recent_projects: Vec<PathBuf>` (`#[serde(default)]`, at most 8, most recent first, updated on open and successful save). File menu gets "Open Recent" listing those that still exist. On launch without `--project`, open the most recent show if it exists and loads; if it fails, open the demo and show the error. `--project` still wins. Add `.lumen.json` double-extension checks: verify natively that "Save as…" produces `Name.lumen.json` (not `.json.json`) and that Open lists it. If `rfd` mangles the double extension, filter on `json` and keep the suggested name.
6. Tests for: relative/absolute round trip, folder move, clash naming in the collect step (pure function), recent list ordering and cap, relink by file name (pure function over a temp dir).
7. Verify natively: build a show with a photo, a video, an audio cue, a logo prop and a PowerPoint deck slide; "Save with media…" into `.local/qa/g3/`; move the folder to another path; open it; everything plays, nothing is missing. Then rename one media file, reopen, use "Locate folder…" to relink it. Quit and relaunch: the last show opens.

## G3.4 Books built into the app (P1, user request, permission granted)

Goal: a fresh install has all 15 books searchable offline at first launch, with no download step. Book text never goes into git: it is fetched into `.local/books/` (gitignored) and copied into the `.app` at package time.

Files: `crates/lumen-library/src/downloader.rs`, a new `crates/lumen-library/examples/fetch_books.rs`, `scripts/package-macos.sh`, `crates/lumen-app/src/books.rs`, `README.md`, `docs/RELEASE.md`, a notice file under `crates/lumen-app/assets/` or `docs/`.

1. **Fetch each page once.** In `run_download`, keep the last fetched `(url, html)` and reuse it when the next unit has the same URL (the plan is ordered, so consecutive units share pages). For Vachanamrut keep both URLs as today. Test with the existing fake fetcher: `diksha` with 10 units makes 2 requests, not 10. This also makes user downloads 5–10× faster for `diksha`, `vato` and `aksharamrutam`.
2. **Fetch script.** `examples/fetch_books.rs <dir>` downloads every catalog book into `<dir>` one after another, printing progress, and skips books whose `book.json` already exists (resume comes free from the cached units). Start it early, in the background, after step 1 is committed: `cargo run --release -p lumen-library --example fetch_books -- .local/books > .local/books/fetch.log 2>&1`. At about 4,939 requests × 1.1 s, expect about 1.5 hours. Keep the 1.1 s rate limit; do not parallelise requests to anirdesh.com. If a book fails (403/404/layout error), record the book, unit and error in STATUS and continue with the others; do not change parsers in this wave unless the failure is a one-line selector fix.
3. **Measure before bundling.** With all books in `.local/books`, record: total size of the `book.json` files; launch-to-search-ready time and RSS of the app with all 15 books installed (the Books worker loads every book and builds `SearchIndex` at launch, so this is new load: today users have 1–3 books). Budget: index ready within 5 s in the background, RSS increase under 400 MB, no hitch in the UI thread. If over budget, stop and write the numbers in STATUS for the orchestrator instead of building a lazy loader yourself.
4. **Package.** `package-macos.sh` copies `.local/books/<id>/book.json` for every catalog id into `Lumen Presenter.app/Contents/Resources/Books/<id>/book.json` (no `units/`). If any catalog book is missing, the release package fails with a clear message, unless `--without-books` is passed (for quick dev packages). Also copy a notice into `Resources/Licenses/Anirdesh-books.txt`: book texts © Anirdesh.com / BAPS, included with permission, not covered by Lumen's MIT licence.
5. **App reads bundled books.** `Books` gets a second, read-only root: the bundle's `Resources/Books` found from `std::env::current_exe()` (`../Resources/Books` relative to `Contents/MacOS/lumen`). In `reload`, for each catalog id use the user's copy in the data dir if it has a valid `book.json`, otherwise the bundled one. A bundled book shows "Included" with "Open book" and no Delete. Books that are neither bundled nor downloaded keep today's Download flow (this is what dev builds without a bundle see). Test: `at_root` with a temp bundled root and a temp user root, covering bundled only, user only, both (user wins), neither.
6. **Download bug, timeboxed to 1 hour.** In a dev build (no bundle), reproduce: start a download, then (a) Cancel and press Download again, (b) quit mid-download and relaunch, (c) disconnect Wi-Fi mid-download (ask the user if you cannot), then press Retry / Download. If you find the cause, fix it at the root with a test. If not, make the panel show "Resume · 173 of 315" for a partial cache (count of `units/*.json`) and append each `DownloadEvent::Failed` reason with the book id and time to `Books/download.log`, so the next failure can be diagnosed. Either way, record what you tried in STATUS.
7. Docs: README "Download" and "Scripture & Books" sections say the books are included (with the notice), the DMG size, and that nothing is downloaded at first launch. `docs/RELEASE.md` gets the `fetch_books` step before packaging. `AGENTS.md`'s "no creative assets in the application source" stays true: nothing book-related is committed.
8. Verify: package with books; mount the DMG; `hdiutil verify`; `codesign --verify --deep --strict`; launch the bundled app with an empty `LUMEN_DATA_DIR`; Cmd+F finds "Gadhada I-1" and a kirtan line with no network (turn Wi-Fi off or block the host and say how). Report the DMG size.
